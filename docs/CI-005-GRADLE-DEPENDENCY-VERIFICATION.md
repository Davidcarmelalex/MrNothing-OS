# CI-005 — Gradle dependency verification

**Status:** implementation prepared; final exact-head CI acceptance pending.

## Purpose

Pin the Android build's resolved external artifacts with Gradle's native dependency-verification mechanism. This complements the existing checksum-verified Gradle 8.9 distribution and immutable GitHub Actions commit references.

## Candidate generation and review

A temporary, read-only CI bootstrap workflow generated SHA-256 metadata from the Android plugin/buildscript graph and the debug/release test, assembly and release-runtime-inventory tasks. It ran independently on the branch push and PR runners for source commit `c4de864f784afab71419f568acad7011b472e451`:

- Push bootstrap run: [42019671946](https://github.com/Davidcarmelalex/MrNothing-OS/actions/runs/42019671946) — success.
- PR bootstrap run: [42019677930](https://github.com/Davidcarmelalex/MrNothing-OS/actions/runs/42019677930) — success.
- Both generated byte-identical metadata: 249 component coordinates, 441 artifact entries and 441 SHA-256 checksums.
- Candidate metadata SHA-256: `1650f08eb3d1006045efc9ea32507245a5464e8126fba10d6e915343876da2ec`.
- The candidate contains Android Gradle Plugin 8.7.3, Kotlin Android plugin 2.0.21 and JUnit 4.13.2 coordinates.
- Gradle generated metadata with `verify-metadata=true`, `verify-signatures=false`, and no ignored-dependency or trusted-artifact bypass entries.

The bootstrap workflow was temporary and is removed in the implementation commit. Its artifact was not blindly trusted: both runner logs were compared and the XML/checksum inventory was structurally checked before inclusion.

## Enforcement

The committed file is `android/gradle/verification-metadata.xml`. All three Android workflows invoke Gradle with `--dependency-verification=strict`. A standard-library Python regression suite validates metadata structure, checksum coverage, core plugin/test coordinates and workflow enforcement.

A disposable negative-control project creates two local Maven artifacts. Gradle must accept the artifact whose bytes match its recorded checksum and reject the tampered artifact whose recorded checksum describes the original bytes. The test runs offline against a temporary Gradle user home and does not alter the repository's dependency cache.

## Scope and limitations

- The metadata covers the dependency artifacts and POM metadata resolved by the candidate-generation tasks. A new configuration or dependency not covered by those tasks must be resolved and added to the reviewed metadata before it is used in a strict build.
- SHA-256 verification detects artifact substitution after the committed checksum is established; it does not independently prove publisher identity.
- Gradle signature verification remains disabled. The initial checksums were generated by two independent GitHub-hosted jobs and compared byte-for-byte, but this is not a substitute for upstream signature verification or an external trust ceremony.
- Repository declarations remain restricted by `android/settings.gradle.kts`: plugin management uses Google Maven, Maven Central and Gradle Plugin Portal; project dependencies use Google Maven and Maven Central. The checksum file does not itself bind a component to one repository URL.
- The negative control is synthetic CI evidence, not a production supply-chain audit.
- No production signing keys, signed release artifacts, device flashing or deployment are involved. CI outputs remain explicitly not for release.

## Acceptance

Final acceptance requires exact-head Phase 1 push/PR, CI-003 push/PR and QA-005 emulator workflows to pass with strict verification active, plus the negative-control step and Python static tests. Until those runs finish, CI-005 remains in progress.
